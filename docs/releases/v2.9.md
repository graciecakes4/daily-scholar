# 2026-09-05

Two PRs, both closing gaps that v2.8 left open. v2.8 split paper discovery into research tracks, and the mechanism worked — but the feed still wasn't focused, for two independent reasons. Within each track only the highest-weight topic was actually being searched. And topics could say which *methods* they cared about but not which *field*, so a track defined around astronomy cross-modal imputation had no way to exclude the far larger medical-imaging literature that shares its vocabulary. **One new migration, zero new dependencies, zero new environment variables.**

## Highlights

### The truncation moved but didn't leave (PR #77)

v2.8 fixed a bug where keyword aggregation across the whole topic scope was truncated to five terms, letting one topic supply every search term. Grouping by track was supposed to fix it. It relocated it.

Aggregation still ran depth-first — it exhausted the highest-weight topic's keyword list before touching the next one. So any topic holding more keywords than the entire budget consumed it alone, just within a smaller pool. On the real topic set, `generative-cross-modal-imputation` has 33 keywords against a budget of five; it supplied all five praxis search terms, and `missing-modality-learning` contributed none despite identical weight. The learnable-token half of the praxis work was in the track, weighted equally, and never searched for.

Aggregation is now round-robin: one value from each topic in turn, tiers still ordered by weight so the highest-weight topic keeps first pick — it just stops taking every pick. Category aggregation had the same shape at `limit=3` and got the same treatment.

```
praxis, before — 1 of 3 topics supplying terms:
  cross-modal generation, cross-modal synthesis, cross-modal imputation,
  conditional diffusion, conditional generative model
praxis, after — 3 of 3:
  cross-modal generation, missing modality, multimodal foundation model,
  cross-modal synthesis, modality dropout
```

The same PR marks `astronomy-foundations` prerequisite-only. A live run had it winning **both** astro slots with general astronomy — ionized nebulae around symbiotic stars, hydrocarbon detection on Titan — rather than the transient work the track exists for, and it was also the topic stretching the track's recency window to 365 days when `transient-photometric-classification` asks for 90. Out of the quota group, the track drops to 180 days.

### Methods and field are different questions (PR #78)

Relevance is `matched_keywords / total_keywords`. A topic that wants broad method vocabulary pays for it twice: the large denominator drags every score down, which forces a low `min_relevance`, and that low threshold then admits papers from every other field sharing the vocabulary. A live run put a brain-MRI inpainting paper and a paper on compiling natural-language specifications into neural functions inside an astronomy praxis track — both had matched enough of "conditional diffusion", "cross-modal", "uncertainty quantification" to clear 0.17.

The only defence available was deleting those terms. But they *are* the methods being tracked. The topic had no way to say "conditional diffusion, in astronomy".

`require_any` is that missing half. When non-empty, a paper must contain one of its terms before any of the topic's keywords are scored at all. Empty — the default, and every existing row — disables it entirely, so nothing changes for topics that don't opt in.

It matches **whole words**, unlike keyword matching, and that distinction is load-bearing. A keyword false positive costs a little score; a gate false positive admits an entire off-domain literature. Under substring matching, "spectra" matches "spectral normalization" and "spectral clustering" — ordinary machine-learning vocabulary — and "clip" matches "eclipse", which in an astronomy corpus fires constantly. The gate would have leaked exactly what it was built to stop. There's a test for that specific case.

Gate terms never enter the denominator, so the lists are generous — 37 astronomy context terms — at no cost to relevance.

The medical missing-modality vocabulary was deliberately **kept**. MICCAI-adjacent work is where learnable modality tokens come from; the gate scopes it to papers that also mention an astronomical context, instead of forcing a choice between losing the method literature and importing all of medical imaging.

### Short acronyms were actively harmful (PR #78)

Pruning the keyword lists turned up something worse than dead weight. Keyword matching is substring-based, so `ECE` matched "pi**ece**", `ViT` matched "gra**vit**y", `CLIP` matched "e**clip**se", and `LoRA` matched "f**lora**". In an astronomy corpus those fire constantly while carrying no signal — they inflate the denominator *and* generate noise. Together with author surnames and a venue name, which effectively never appear in an abstract, three topics lost 33 → 27, 28 → 24 and 33 → 29 keywords. Generic-but-core phrases stayed; the gate is what makes them safe.

## Migration shape

**One new migration, additive with an idempotent guard, no destructive changes:**

- `0017_topic_require_any` — adds a JSON `require_any` column to `topics`, defaulting to an empty list. Parent: `0016_topic_track`. Single head. Verified to upgrade, downgrade and re-upgrade cleanly against a copy of the dev database.

An empty list disables the gate, so every pre-existing topic scores exactly as it did before.

## Notes

- **`python scripts/assign_topic_tracks.py --apply` is required post-deploy**, and carries more than it did in v2.8 — the domain gates and pruned keyword lists as well as the track assignments. `config/topics/private/` is gitignored, so the database is the only place that configuration exists. Skip it and the `require_any` column ships empty and this release changes nothing.
- **No new Python or npm dependencies. No new environment variables.**
- **Tests**: 14 new tests. Seven cover the shared keyword budget — every topic contributing under a lopsided 33/3/2 split, weight-order precedence, the budget cap, case-insensitive dedupe, category aggregation, the single-topic path, empty lists. Seven cover the gate, including that it does not match inside a longer word. Full suite: **346 passed, 1 skipped, 0 failed.**
- **Pre-release verification ran against `develop`**: migration applied and at head, all three topic columns present, every topic already matching the intended configuration, both tracks in scope, `astronomy-foundations` prerequisite-only, suite green.
- Full changelog entry: `CHANGELOG.md` under `[v2.9]`.

## Followups

- **An untracked remainder still gets its own paper quota.** With `scope_mode='all'` the leftover topics are grouped into one bucket that `select_daily_papers()` treats as a peer of the real tracks. Round-robin made its character worse rather than better: it used to search five terms from a single foundations topic, and now samples five unrelated fields at once — atmospheric physics, cell biology, classical mechanics, climate, financial economics. Scoping to the tracked topics works around it today, but the code should probably not treat leftovers as a track you deliberately defined.
- **Within a track, the loosest topic still sets the threshold.** Astro's `min_relevance` is 0.17, inherited from the demoted `sim-to-real-transfer-astronomy`, rather than the 0.18 its primary topic asks for. The same shape as the scope-wide problem v2.8 fixed, one level further down.
- **`scripts/check_track_balance.py`'s "BEFORE" comparison no longer reproduces the old behaviour.** It calls the live `_aggregate_keywords`, which this release changed, so the branch labelled BEFORE now reports round-robin over the whole scope rather than the depth-first path it is describing. It prints "5 of 22" where the true pre-v2.9 figure was "1 of 22". A measurement tool that misreports its own baseline is worth fixing before it's trusted again — freeze that branch as an inline loop.
- **The 0.6 keyword / 0.4 category weighting** lets a paper accumulate meaningful relevance from arXiv category overlap alone, which is part of why thresholds behave less intuitively than the keyword lists suggest.
- **No frontend surface for tracks or gates**, though both fields are on the API responses.
