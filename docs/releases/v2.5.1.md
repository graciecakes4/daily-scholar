# 2026-07-03

Small polish release. Three PRs land: admin-generated invite codes gain an optional custom-text option instead of always being random, the dashboard's stats bar is redesigned to match the editorial theme instead of standing out as a leftover generic-SaaS blue gradient, and a flexbox bug that could clip the sidebar's "in scope" card down to a sliver is fixed. **Zero new migrations, zero new dependencies, zero new environment variables.**

## Highlights

### Custom invite codes (PR #56)

Admins generating an invite code from `/settings/admin`'s Invite codes tab previously only ever got a random `secrets.token_urlsafe` string. A new "Custom code" text input sits next to the Create button: left blank, behavior is unchanged (still a random code); filled in, the typed value is validated (3–32 characters, letters/digits/`-`/`_`) and used as-is.

`generate_invite_code()` (`backend/services/invite_codes.py`) takes an optional `custom_code` parameter. When given, it's checked against the charset/length rule and for a collision with an existing code — no retry-on-collision here, since silently handing back a different code than the admin typed would be more confusing than a clear error. `InviteCodeInvalid` (bad format) and `InviteCodeTaken` (collision) are new exception classes, mapped to `400` and `409` respectively in `backend/api/admin_invites.py`'s `create_invite` handler. The random-code path (`_new_code_string()` + its 5-attempt uniqueness retry loop) is untouched.

### Dashboard stats bar redesign (PR #57)

The streak / papers-seen / archived / quiz-accuracy bar at the top of the dashboard was still styled as a `bg-gradient-to-r from-blue-600 to-indigo-600` band — a holdover from before the editorial sidebar/settings redesign in v2.4–v2.5, and visibly inconsistent with the Fraunces-serif, warm-paper, gold-accent system used everywhere else.

Three directions were explored as throwaway HTML mockups (kept locally under the gitignored `mockups/` folder, not in this diff) before picking one: a quiet hairline "masthead ledger" strip, a row of bordered "numbered cards" pulling the roman-numeral eyebrow pattern already used in earlier sidebar mockups, and a dark amber "night observatory" instrument-panel look as a deliberate free-choice departure. The numbered-card direction shipped — four `bg-paper-2` cards (Streak, Read, Kept, Accuracy) with italic roman-numeral labels (`I · Streak`, `II · Read`, etc.) and large Fraunces numerals; the streak card is the visual hero, with a rust-to-gold top accent bar where the other three get a quiet rule-colored one. `FireIcon` (`frontend/app/page.tsx`) gained an optional `className` prop so it could be recolored/resized for the smaller card icon without duplicating the component.

The dark "observatory" mockup was liked enough to keep around: a code comment now marks it as a candidate for a future user-selectable theme preference (not just a one-off palette swap) rather than being discarded — see Followups below.

### Sidebar "in scope" card clipping fix (PR #55, PR #56)

`ActiveScopeChip` (the pinned "in scope" card at the top of the left rail) could render clipped down to a ~26px sliver — just the "IN SCOPE" label, with the scope name, topic count, and "Change scope" link cut off — whenever the sidebar's total content ran taller than the viewport. Root cause: the card is a flex item inside the flex-column `<aside>`, and it also has `overflow-hidden` (needed to clip its diagonal-hatch background to the rounded corners). Setting `overflow` to anything but `visible` on a flex item removes that item's automatic minimum-size floor, so it was the one item in the rail flexbox could shrink below its own content size instead of the others when space ran short.

Fixed by adding `shrink-0` to all three render states (loading skeleton, empty prompt, ready card) so the component can never be compressed below its content regardless of what else is in the rail. This fix was independently made twice — once in PR #55's general frontend cleanup, once in PR #56 while testing the invite-code feature — landing in a trivial merge conflict (both sides added the same class, just in different attribute order) that was resolved by keeping `shrink-0` in place.

### Deployment doc correction (PR #55)

`frontend/railway.toml`'s comments still described the pre-v2.4 deploy shape — `NEXT_PUBLIC_API_URL` as a required build-time variable. Since v2.4's same-origin `/api/*` proxy, the actually-required variable is `BACKEND_INTERNAL_URL`, with `NEXT_PUBLIC_API_URL` now an optional escape hatch (that additionally requires `COOKIE_DOMAIN` on the backend if used, or CSRF double-submit breaks cross-subdomain). Comments updated to match what's actually been true since v2.4; no behavior change.

## Followups

- **Observatory theme as a user preference.** The dark amber "night observatory" stats-bar mockup (`mockups/stats_bar_option3_observatory.html`, not committed — see the gitignore note in v2.4's release notes) is a good candidate for a proper user-selectable alternate visual theme rather than a one-off swap. Would need a persisted preference (e.g. a `users.theme` column) plus a toggle in `/settings/account`, and the relevant components reading that preference to pick a variant. Marked with a `TODO(design)` comment in `frontend/app/page.tsx`; not built yet.
- **Custom invite codes have no admin-facing "already exists" duplicate-check-before-submit UX** — the 409 comes back only after the admin clicks Create. Fine for now given how rarely admins hit a real collision, but a live-availability check would be a nice small follow-up if this gets used more.
