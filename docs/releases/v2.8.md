# 2026-09-04

Three PRs, and the through-line is that every one of them fixes something that had been silently doing nothing. Paper discovery was querying one topic out of seven. The auth session lookup was stranding the object it returned, 500ing the first request after every login. The PR review workflow was cancelling itself before it read a line of the diff. Each failed in a different invisible way — no error at all, an error attributed to the wrong layer, and a red check that never examined anything. **One new migration, zero new dependencies, zero new environment variables.**

## Highlights

### Research tracks, or: why weight tuning could never have fixed this (PR #73)

`PaperDiscovery.discover_papers()` built its search by aggregating keywords across every topic in scope, sorted by topic weight descending, then truncating to the top five. That truncation happened *before* weights were used for anything else, which is the part that matters: no amount of adjusting weights could surface a topic whose keywords didn't make the cut, because the cut came first.

Run against the live topic set, the numbers were worse than "one track dominates." All five search terms came from a single topic — `transient-photometric-classification`, at weight 2.0 — and **one of seven topics contributed any search term at all.** The praxis side of the work (diffusion models, learnable tokens, cross-modal imputation) was not underweighted in the results; it was never queried. `_scope_min_relevance()` compounded it by taking the *lowest* threshold anywhere in scope and `_scope_max_recency()` the *widest* window, so the single most permissive topic set the bar for everything else.

Topics now declare a `track`. Discovery groups by track and runs a full pass per group, so each track gets its own five-keyword budget, its own arXiv categories, its own recency window and its own relevance threshold. Papers are scored only against their own track's topics, so a strong praxis paper is no longer penalised for failing to match astro keywords. `select_daily_papers(quota_per_track=N)` then guarantees N papers per track rather than N overall, with cross-track duplicates resolved to whichever track scored the paper higher so one paper can't fill two quotas.

A track that has nothing above its threshold returns fewer papers rather than borrowing the other track's slots. That's deliberate: backfilling would hide exactly the failure this change exists to fix, and an under-filled day is useful signal that a track's keywords or threshold need attention.

Scopes that never declare a track collapse into a single untracked bucket and take the original code path unchanged, so this is opt-in for everyone else.

Alongside it, `prerequisite_only` marks foundations topics — `ml-foundations` is set this way — that should keep informing review and quiz generation but never consume a daily paper slot. Previously those topics competed for slots against the work the track exists to follow.

### A v2.7 regression that presented as "the backend is down" (PR #74)

The `last_seen_at` throttle added in v2.7's `li6` work introduced a commit into `lookup_session_user()`:

```python
if row.last_seen_at is None or (now - row.last_seen_at) > SESSION_LAST_SEEN_THROTTLE:
    row.last_seen_at = now
    session.commit()      # expires every object in the identity map,
                          # including the User loaded a few lines above
session.expunge(user)     # detaches an already-expired object
return user               # first attribute read -> DetachedInstanceError
```

`expire_on_commit` defaults to `True`, so the commit expired the `User`, and expunging an expired instance produces one that can never reload itself. The first attribute read — `user.status`, inside `_resolve_session_user_id()` — raised `DetachedInstanceError`.

What made this hard to see is the timing. The throttle fires when `last_seen_at IS NULL`, which is true for every brand-new session, and then once per fifteen minutes. So an authenticated request 500s immediately after login, works fine for the next fifteen minutes, 500s again, and repeats. And because it's a 500 on the auth dependency rather than a 401, the frontend surfaces it as a connection failure rather than an auth failure — including on endpoints like `/health` that have no auth involvement whatsoever, which sends you looking at ports and proxies instead of at session handling.

The fix is to expunge the user before the session-row write, so the commit has nothing of ours left in the identity map to expire. Every other `expunge()` site in the codebase — nine of them have a `commit()` nearby — already guards this with `commit() -> refresh(obj) -> expunge(obj)`. That would work here too, but `user` isn't the object being written (`row` is), so refreshing it would re-read a row we already hold purely to undo an expiry we caused, and it would introduce an `ObjectDeletedError` path for a concurrently deleted user on a function that already handles that case cleanly. The reasoning is written into a comment at the call site, because the obvious "consistency" refactor would put the bug straight back.

Nothing in the suite called `lookup_session_user()` directly, which is how this shipped. `backend/tests/test_session_lookup.py` now covers the throttle-fires path, the throttle-skipped path, a stale `last_seen_at`, that the `last_seen_at` write still lands after the fix, and stability across repeated lookups.

### The review workflow had been reviewing nothing (PR #75)

`claude-review.yml` still passed `direct_prompt` and `timeout_minutes` to `claude-code-action@v1`, which accepts neither. Unknown inputs are warned about and dropped rather than failing the step, so the action started with an empty prompt, logged `Context prompt: NO PROMPT`, resolved `Trigger result: false`, and cancelled its own job. GitHub renders a cancelled job the same as a failed one, so every PR carried a red check that had never looked at the diff.

`direct_prompt` becomes `prompt` (a documented drop-in rename in v1) and the timeout moves to the job level. The prompt text is unchanged; the repo and PR number are now prepended so the agent is told which PR it's reviewing rather than inferring it.

## Migration shape

**One new migration, additive with idempotent guards, no destructive changes:**

- `0016_topic_track` — adds `track` (nullable `String(50)`, indexed) and `prerequisite_only` (`Boolean`, NOT NULL, `server_default false`) to `topics`. Parent: `0015_session_last_seen`. Single head, no branching. Verified to upgrade, downgrade and re-upgrade cleanly against a copy of the dev database.

Existing rows land on `track=NULL` / `prerequisite_only=false`, which is inert — discovery falls back to its pre-v2.8 behaviour until tracks are assigned.

## Followups

- **The live discovery pass ran, and both tracks returned papers** — two astro, two praxis — confirming the mechanism end to end. It also surfaced three things worth acting on before trusting a day's output.

  **An untracked remainder turns into a third track.** `scope_mode='all'` is the default, so all 22 active topics are in scope: the two real tracks plus twelve seeded starter foundations topics and three user-created ones. Those fifteen get grouped into a single untracked bucket, and `select_daily_papers()` gives every bucket a quota — so the untracked leftovers become a third stream. In this run they produced the two highest-scoring papers overall (climate science at 0.335, statistical mechanics at 0.315), both outranking anything in the actual research tracks. The grouping was written so that a scope with *no* tracks behaves exactly as it did before; the case it doesn't handle is a scope with *some* tracks, where the remainder should probably not be treated as a peer of the tracks you deliberately defined. Scoping to the tracked topics (`scope_mode='multi'`) works around it today.

  **Inside the astro track, `astronomy-foundations` is doing the winning.** Both astro selections matched it rather than `transient-photometric-classification` — ionized nebulae around symbiotic stars, and hydrocarbon detection on Titan. Good astronomy; not time-domain work. It is also the topic stretching the track's recency window to 365 days when the transient topic asks for 90. Marking it prerequisite-only would mirror what `ml-foundations` already does on the praxis side, and is the obvious next step — held back here only because it would leave one topic feeding the astro quota, and whether that clears the threshold on a given day is untested.

  **The praxis selections were weak.** 0.196 and 0.176 against a 0.17 floor, and off-domain: an SSIM-aligned refiner for brain-MRI inpainting, and a paper on compiling natural-language specifications into neural functions. Both plausibly match keywords like "cross-modal" and "conditional diffusion" while having nothing to do with astronomy. That's a keyword-tuning problem rather than a code one, but it means the track is currently scraping its own threshold rather than finding the work it was defined for.
- **Within a track, the loosest topic still sets the parameters.** `_scope_min_relevance` takes the lowest value in a track and `_scope_max_recency` the widest — the same shape as the scope-wide problem this release fixed, one level down. On the current astro scope `astronomy-foundations` (365 days) widens the whole track's window despite `transient-photometric-classification` asking for 90, and the demoted `sim-to-real-transfer-astronomy` (0.17) sets the threshold rather than the primary topic's 0.18. Narrowest-wins versus weight-weighted is a preference call, left open deliberately rather than guessed at.
- **No frontend surface for tracks.** `track` is on the API response and on `Paper.to_dict()`, so the data is there; track badges and a track-sectioned daily view are not built.
- **Whether `astronomy-foundations` should also be `prerequisite_only`** is unresolved — it's the astro-side mirror of `ml-foundations`, but demoting it would leave `transient-photometric-classification` as the only topic feeding the astro quota.
- **`on.pull_request.branches` lists `feature/**`, `bugfix/*` and `release/*`**, but that filter matches the PR's base branch, not its head. Everything targets `develop` or `main`, so those entries match nothing today.
- **Backend `pytest` still isn't run in CI**, carried forward from earlier releases. The suite is green as of this release, which makes wiring it up cheaper than it has been at any prior point.
