# 2026-07-02

Settings IA rebuild + AI-assisted scope creation release. v2.4 rebuilt navigation around the scope library; **v2.5 finishes the job by giving Settings itself a real hierarchy** — Scope, Notifications, Account, Tutorials, and Admin are now sibling sections instead of being split across two route trees with inconsistent per-page "related link" clusters filling the gaps. On top of that, **scope creation gains an AI-drafting path**: a new "Generate scope" wizard, reachable any time from Settings > Scope rather than only during first-run onboarding, turns a title and description into a draft set of keywords, arXiv categories, and key concepts — reviewed and edited as bubbles instead of raw text — before creating a topic and wrapping it in a single-topic scope. Also folds in the prior notifications-page redesign (plain-English schedule summaries in place of the raw cron string) and an iOS Safari bottom-nav anchoring fix (#50). **Zero new migrations, zero new dependencies, zero new environment variables.**

## Highlights

### Settings information architecture restructure (PR #51)

Settings previously split across two top-level route trees — `/scopes/*` for scope-related pages, `/settings/*` for everything else — with Notifications nested awkwardly under Account, no nav entry for Admin at all, and every scope/account page carrying its own "Browse public →" / "Access requests →" / "Account →" link cluster just so users could get around.

New structure: `/settings/scope/library`, `/settings/scope/browse`, `/settings/scope/requests`, `/settings/scope/new` all under Scope; `/settings/account/profile`, `/settings/account/password`, `/settings/account/username` under Account; `/settings/notifications` promoted to its own sibling section; `/settings/tutorials` new; `/settings/admin` now properly surfaced in nav. Old bare `/settings/scope` and `/settings/account` redirect to their library/profile pages via Next.js Server Component `redirect()`, so existing bookmarks don't 404.

Sidebar and MobileTabBar were rebuilt to mirror this exactly and are now the single source of truth for cross-section navigation — every scope/account/notifications/tutorials/admin destination is listed directly in nav, so the scattered per-page link clusters were removed rather than redesigned in place. Admin is a real nav entry for the first time (`Sidebar()` previously never called `useAuth()` at all, so there was no way to conditionally show it).

The tour-replay picker — previously implemented three separate times (`Sidebar.tsx`'s `HelpGroup`, `MobileTabBar.tsx`'s `helpView` state, and the account page's `TourReplayCard`, each independently maintaining the same `TOUR_CHOICES` array, flagged as known debt in v2.4's release notes) — is now one page, `/settings/tutorials`, that both nav surfaces link to.

Two deliberate scope-limiting decisions: `/scopes/picker` was kept as its own route (it serves the first-run onboarding flow gated by `ScopePickerGuard`, a distinct concern from general scope creation) rather than merged into `/settings/scope/new`; and `ScopePickerGuard`/`OnboardingGuard`'s `SKIP_PREFIXES` needed no changes at all, since both already matched `/settings/scope` as a prefix covering every route moved underneath it. `ScopeTour`'s `fire_on_path` did need an explicit update to `/settings/scope/library`, since `useDriverTour` gates on an exact pathname match rather than a prefix.

### Generate-scope wizard (PR #52)

The AI-drafting capability behind this — `generate_topic_draft()`, backing `POST /onboarding/generate-topic` — already existed server-side, but was only ever called from the first-run onboarding wizard. It turns out it isn't actually onboarding-gated: the endpoint only requires a real signed-up user, nothing checks onboarding state. So the new `/settings/scope/generate` page just reuses the existing `generateTopicDraft()` client directly from a page reachable any time.

Flow: title + description in → drafted keywords / arXiv categories / key concepts come back → the user reviews and edits the draft (nothing saved yet) → approving creates a `Topic` via `POST /topics`, then wraps it in a `scope_mode='silo'` `Scope` via `POST /scopes`. The new scope lands in the library but does not auto-activate — same mental model as forking or picking a starter scope, the user switches to it manually.

The review step uses a new reusable component, `ChipListEditor` — the first chip/tag-style editor in the codebase (the existing convention, `TopicForm.tsx`, edits `string[]` fields as raw newline/comma-split textareas). Click a chip to select it, then Edit or Delete via a small toolbar rather than cluttering every bubble with icon buttons; a separate dashed "+ Add" chip reveals a text input with an optional autocomplete dropdown. Recommendations only ever show up in that add flow, never while editing an existing chip, since editing is a deliberate one-off correction rather than a search. Suggestion pools are drawn from the user's own visible topic catalog (real keywords/concepts already in use, via the existing `listTopics()`) rather than fabricated — the arXiv categories field additionally gets a static, curated real taxonomy list merged in, since that field (unlike free-form keywords) has a genuinely fixed, stable set of valid codes.

The two-phase create (topic, then scope) has distinct error handling for each phase: if topic creation fails, nothing is saved and retry is clean; if the topic succeeds but the scope wrap fails, the error message explicitly says the topic was saved to the catalog, so nothing silently vanishes and the user isn't left wondering where their draft went.

Backend test coverage: `POST /topics` had zero test coverage anywhere in the suite despite real branching logic (regular-user ownership stamping, ignoring a user-supplied id, visibility defaults, admin-only id/owner overrides) — closed with a new `backend/tests/test_topics.py` (5 tests). Also closed a gap in the existing silo-mode tests: every prior test asserted *rejection* (0 or 2 topic ids); none confirmed the actual success path with exactly one id, which is the mode this entire feature depends on — added `test_silo_with_exactly_one_topic_succeeds`. Full backend suite verified at 353 passed, 1 skipped (3 pre-existing, unrelated push-subscription failures noted below).

### Human-readable notification schedules (PR #50)

Each notification card now leads with a plain-English schedule sentence ("Every day at 9:00 AM") built from the underlying cron expression, with the raw cron tucked behind a small info affordance for devs/power users instead of being the primary UI. New `to12h`/`to24h`/`fmt12` helpers back a 12-hour time stepper in place of the old raw `HH:MM` text field. If a power user has hand-edited the notification JSON to something the friendly picker can't parse, it falls back to a raw, editable cron field rather than silently overwriting an exotic schedule.

Also fixed during this cycle: `NotificationDispatchResult.result` can carry a nested `skipped` reason (e.g. VAPID unconfigured, no push subscriptions) distinct from a top-level `skipped` (the content builder itself had nothing due today) — the UI only checked the top-level field, so a real skip reason from the fanout layer could go unreported as a bare "sent to 0 devices" with no explanation.

### iOS Safari bottom-nav anchoring fix (PR #50)

`MobileTabBar`'s fixed-position bottom nav lacked its own GPU compositor layer, which iOS Safari renders as the nav "floating" / lagging behind page content during momentum scroll — worse while the dynamic toolbar is mid-collapse. Fixed by promoting the nav to its own layer via `transform: translateZ(0)` plus `WebkitBackfaceVisibility: hidden`.

## Migration shape

**Zero new migrations.** Nothing in this cycle touches the schema — the generate-scope wizard's new `Topic`/`Scope` rows go through the existing `POST /topics` and `POST /scopes` endpoints unchanged.
