# 2026-07-05

Self-serve password reset, the admin console's final three tabs, and a from-scratch theming system. Seven PRs land: real SMTP-delivered password reset (`li3b`), Admin Topics/Cache/Stats tabs closing out Phase 2 (`ad4`/`ad5`), and five rounds of theme work (`fd3` foundation + six more themes + two accent pickers + a random-rotation meta-theme, plus `fd2`'s independent reading-font picker). **Two new migrations, zero new dependencies, one new optional env-var family (`SMTP_*`).**

## Highlights

### Self-serve password reset via SMTP (PR #59, li3b)

Locked-out users previously had no way back into their account except asking an admin out-of-band. `POST /auth/forgot-password` now looks up the account by email and, if it's active, emails a link containing a single-use `password_reset_tokens` row (30-minute TTL) via `backend/services/email.py` — a plain stdlib `smtplib` wrapper, not a third-party email SDK. `POST /auth/reset-password` consumes the token and sets the new password. The endpoint always returns the same generic "if that account exists, check your email" response regardless of whether the email actually matched an account, so it can't be used to enumerate registered users.

Configuration lives in a new `SMTP_*` env-var family (`.env.example`) — host, port, TLS mode, credentials, from-address. Every field is optional: leave `SMTP_HOST` blank and the backend logs the reset link to the console instead of sending it, so the whole flow works in local dev with zero setup. New pages `frontend/app/forgot-password` and `frontend/app/reset-password` match the existing `AuthShell` styling, and the login page now links to forgot-password. Both endpoints are IP-rate-limited through the existing middleware.

An earlier iteration of this feature verified identity with an email+username knowledge check rather than real email — no proof the requester actually owns the inbox. Replaced once SMTP was wired up, since inbox-ownership is the correctly-scoped check for a password reset.

### Admin console's final three tabs (PR #60, ad4 + ad5)

Phase 2 scoped seven admin tabs; four (Approvals, Invites, Users, Audit log) already shipped in earlier releases. This PR lands the remaining three, closing the phase out.

**Topics** wires already-existing backend endpoints (`POST /topics/import-yaml`, `POST /topics/export-yaml`, `GET /topics?include_orphaned=`) into an actual UI — import/export buttons with a result summary, an orphaned-only filter, and badges distinguishing active/orphaned and system-vs-user-owned topics.

**Cache** adds `DELETE /admin/cache/{user_id}`, clearing every `daily_content_cache` row for one targeted user (looked up via the same account list the Users tab already fetches). Every bust is audit-logged. Deliberately scoped to a single user per action — a multi-select and a global "clear for everyone" option are real follow-ups, but coarse and effectively irreversible enough to deserve their own design pass rather than being rushed into this PR. Captured as a new Phase 6 in `FUTURE_FEATURES.md`.

**Stats** is the most built-out of the three: `GET /admin/stats/overview` (user counts by status, content volume, 30-day signup trend) and a considerably deeper `GET /admin/stats/quiz-performance` — overall/median/average score, a score distribution, per-topic and per-difficulty accuracy breakdowns sorted worst-performing-first, a 30-day score trend, and two leaderboards (most active, and highest accuracy gated behind a minimum-questions floor so one lucky quiz can't top the board). Everything is derived from the `ArchivedQuiz.questions` JSON already stored per quiz — no new instrumentation needed — and all aggregation is fetch-then-bucket-in-Python rather than dialect-specific SQL, since `date_trunc`/`strftime` differ between SQLite and Postgres and this is fine at beta scale. No charting library exists in this project, so the bars, score-trend sparkline, and leaderboards are hand-rolled CSS.

### A theming system, from zero to ten themes (PRs #61–#64, fd3)

Four PRs across two days build out fd3's entire theme backlog.

**The foundation (PR #61)** adds a `display_settings` JSON column to `user_settings`, a backend registry (`backend/services/display.py`), and a `/settings/display` settings page with live preview — pick a theme or font size and it applies immediately, Save just persists it. The load-bearing technical decision here: Tailwind's color palette moved to CSS custom properties as space-separated RGB-triplet strings, wrapped as `rgb(var(--x) / <alpha-value>)` — the only pattern that keeps Tailwind's `/NN` opacity modifiers (`bg-rust/5` and friends, used all over the app) working with CSS-variable-driven colors. A bare `var(--x)` hex string builds without error but silently drops any opacity-modified utility, which surfaced as a real, only-caught-by-directly-compiling-and-grepping bug while building this out. Three themes ship in this PR — editorial (the existing look, now themeable), dark (same layout, recolored), and observatory (a near-black instrument panel with an amber glow and Bodoni Moda numerals) — plus four font sizes, and an app-wide sweep converting roughly 1,000 hardcoded legacy Tailwind color classes across 29 files (plus background/text classes on 57 native form controls that had none at all) to theme tokens, so dark/observatory actually render correctly everywhere instead of just on pages built after the fact.

**Three more themes (PR #62)** — Soft Morning (blush pastel, rounded shapes, Fraunces + Nunito), Noir (cold true grayscale, deliberately no warm undertone unlike observatory's amber glow, Bebas Neue + Work Sans), and Brutalist (stark black/white, thick hard-edge borders, offset shadows, Archivo Black + Space Mono — with `--rule` repurposed as solid near-black so every existing border utility reads bold for free, plus a scoped `border-radius`/`box-shadow` reset, giving the hard-edge look without touching a single component).

**Colorful accents (PR #63)** turn Soft Morning and Noir into the two themes with a genuine multi-hue picker — five accents each, swapping only `--gold`/`--gold-dark`: orange/rose/sage/sky/lavender for Soft Morning (pastel-weight), cobalt/crimson/emerald/violet/amber for Noir (fully saturated, since a pastel tint would vanish against near-black).

**The last three themes plus Random (PR #64)** — Muted (desaturated stone/greige, a single dusty-clay accent, Cormorant Garamond headlines over an otherwise-untouched Inter body, so the "quiet" identity comes from restraint rather than a font takeover), High Contrast (pure black/white checked against real WCAG contrast ratios — body text 21:1, secondary text 9.6:1, non-text borders 4.1:1, all comfortably past AAA; the one danger red sits around 6.9:1, clearing AA — with Atkinson Hyperlegible, a typeface purpose-built for low-vision readability, replacing both the display and body face, plus its own 4-accent picker), and Pride (a clean, warm-neutral base in Fredoka + Figtree, with the progressive pride flag's full palette — black, brown, light blue, pink, white, plus the classic six — carried as a decorative gradient ribbon pinned to the top of the viewport, not a full recolor of the interface).

Random is the odd one out architecturally: it's not a palette at all, just a hash. `resolve_random()` combines a user's ID, a purpose tag, and the current ISO week (Monday-anchored, UTC) through `crc32` to land on one of the other nine themes — and that theme's own accent, if it has one — with no cron job, scheduler, or stored rotation state anywhere. The ISO week number is the clock: it changes at the Sunday/Monday boundary for free, which is exactly the reset behavior wanted. A standalone test harness confirmed the same pick holds for repeat calls within a week, flips at exactly Sunday 23:59 → Monday 00:01 UTC, and spreads roughly evenly across all nine real themes over 2,000 synthetic users. `/settings/display` surfaces a small "This week: `<theme>` · `<accent>`" caption so picking Random isn't a total mystery.

One regression shipped and was caught before this release closed out: after Random's resolved-vs-stored split landed, clicking a theme card on `/settings/display` stopped visually previewing anything — Save still worked, since the server always returns a fresh `resolved_theme`, but the click handler wasn't mirroring the pick into the locally-held `resolved_theme` field the preview actually paints from. Fixed in the same PR.

### Reading-font picker for generated content (PR #65, fd2)

By the time fd3 wrapped, every theme had its own bespoke typography — Bebas Neue for Noir, Archivo Black for Brutalist, Cormorant Garamond for Muted. fd2's "add new fonts" (Merriweather, Source Sans 3) predates all of that, so rather than layering a font override on top that would undo each theme's own identity, it landed scoped specifically to `.prose-scholar` — the class that already wraps generated topic reviews and paper summaries. A new theme-independent `reading_font` setting (`theme`/`merriweather`/`source_sans`) drives a `[data-reading-font="..."]` override on that one class only; picking "Match theme" (the default) applies no override at all.

While touching that block, a pre-existing gap surfaced: `.prose-scholar` was still on hardcoded `slate`/`blue` Tailwind classes, missed by the fd3 sweep since it lives in `globals.css` rather than a page file. Fixed alongside the font work — code blocks specifically use an inverted `ink-2`/`paper-2` pairing rather than the `gold-dark` swap used for `slate-900` elsewhere, since a code block should read as a neutral dark surface on every theme, not an accent-colored one.

## Migration shape

**Two new migrations, both additive with idempotent guards, no destructive changes:**

- `0013_password_reset` — new `password_reset_tokens` table (single-use, short-lived tokens for the forgot-password flow).
- `0014_display_settings` — new `display_settings JSON` column on `user_settings`, mirroring the `notification_settings` column pattern from `0004`.

## Notes

- **No new Python or npm dependencies.** Email sending uses stdlib `smtplib`; the Stats tab's charts are hand-rolled CSS rather than a charting library.
- **New optional env-var family**: `SMTP_HOST` / `SMTP_PORT` / `SMTP_USE_TLS` / `SMTP_USERNAME` / `SMTP_PASSWORD` / `SMTP_FROM_EMAIL` / `SMTP_FROM_NAME`. All optional in dev/CI (blank `SMTP_HOST` falls back to console-logging); **production needs these set for password reset to actually send mail.**
- `docker-compose.yml`'s `FRONTEND_URL` was pointed at the compose-network-only `http://frontend:3000`, which broke local-dev password-reset link clickability (CORS worked regardless via a hardcoded `localhost` fallback, masking the bug until a real link needed clicking). Fixed to `http://localhost:3000`.
- `docs/DEPLOY.md` updated with `SMTP_*` guidance for the Railway dev+prod split.
- **Tests**: `tsc --noEmit` clean and a direct Tailwind CLI compile (confirming every new theme/accent/font selector resolves with no collisions) across all four theme PRs. `resolve_random()` verified via a standalone Python harness (determinism, week-boundary reset, distribution). No new automated test suite — same gap noted in prior releases; see Followups.
- Full changelog entry: `CHANGELOG.md` under `[v2.6]`.
